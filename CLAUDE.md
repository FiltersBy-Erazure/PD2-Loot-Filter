# Erazure PD2 Loot Filter: working rules

## What this repo is
- A Project Diablo 2 (PD2) loot filter published to players through the PD2 launcher.
- `Erazure-Main.filter` is the ONLY file edited by hand. It is the source of truth.
- The other 7 `.filter` files are GENERATED by `python tools/build_variants.py`. Never edit them
  (a deny rule in `.claude/settings.json` blocks it). They differ from Main only in which 3-line
  alias block is active in the "Toggles" section (`BIG_GG`, `POE_SOUNDS`, `REVEALED`).
- `filter_definitions.json` lists the 8 variants for the launcher. Each `display_name` must match a
  `//  Erazure - ...` header in the Toggles section.
- Longer background (section map, rule counts, roadmap): `HANDOFF.md`. Read it for big tasks.

## Searching (the file is ~8,500 lines / ~200k tokens; never read it whole)
- Search `Erazure-Main.filter` ONLY. Never grep `*.filter`: every hit comes back 8 times.
- Read line ranges around hits instead of whole sections.
- References, searched on demand (never @-import them here, they are large):
  `docs/pd2-item-filtering.wiki` (syntax, keywords, conditions), `docs/pd2-item-codes.wiki`,
  `docs/pd2-filter-info.wiki`, `docs/pd2-formula-info.wiki`, `docs/patch-notes/`.

## After ANY edit to Erazure-Main.filter
1. A PostToolUse hook re-runs `tools/build_variants.py` automatically. If it reports an error, fix it.
2. Run `python tools/build_variants.py --check`. It must print "All 8 filters in sync."
3. Show the diff of `Erazure-Main.filter` only (the variants mirror it).

## File format: preserve exactly
- Encoding: UTF-8 without BOM. Since PD2 Season 13, UTF-8 displays extended characters
  (•, ÿ, §, ¹²³) correctly. Do NOT convert to ANSI/Windows-1252, even though the wiki says to.
- Line endings: CRLF. Do not normalize to LF.
- `ÿc` + a character is an in-game color code (used in `ItemDisplayFilterName` lines). Never "fix" it.
- Many rules end with a trailing `//`. Match the style of the surrounding rules.
- Never reformat, re-indent, reorder, or "clean up" lines you were not asked to change.
  Diffs must be minimal: every stray change reaches players.

## Filter semantics
- Rule format: `ItemDisplay[conditions]: output`. Lines starting with `//` are ignored.
- Rules are evaluated TOP TO BOTTOM. The first matching rule WITHOUT `%CONTINUE%` decides the
  item's display and stops evaluation. Order is behavior.
- `%CONTINUE%` stores the rule's output into `%NAME%` and keeps evaluating. ~77% of rules are
  `%CONTINUE%` layers; later rules see the modified `%NAME%`.
- An empty output (`ItemDisplay[...]:` or output only inside `{}`) HIDES the item's name.
- Notification keywords (`%BORDER-xx%`, `%MAP-xx%`, `%DOT-xx%`, `%PX-xx%`, `%SOUNDID-n%`) are applied
  in a separate pass: they fire even if an earlier rule stopped evaluation. Without `%TIER-n%`
  they act as `%TIER-9%` (notify at all levels).
- `FILTLVL` gates rules by the player's selected strictness (0 = Show All, 1–12 custom). The 12 levels
  are the `ItemDisplayFilterName[]` lines at the top; their order = their number.
- Aliases (`Alias[X]:...`) are find-and-replace at load time. `TRUE`/`FALSE` aliases are how
  variant toggles work (e.g. `ItemDisplay[BIG_GG ...]`).
- Limits: name ≤ 56 displayed / ≤ 125 internal chars (each color keyword costs 3, `%NL%` costs 2).
  Descriptions ≤ 500 chars.
- `{}` = description text. `%CONTINUE%` only works outside braces.
- The last rule is the catch-all `ItemDisplay[]:%NAME%{%NAME%}//`. Nothing goes after it.

## Before adding or changing a rule
1. Search Main for every rule touching the same item code / group / stat
   (e.g. `r30`, `RUNE>29`, `STAT127`, `amu`). List them with line numbers.
2. Decide where the new rule must sit relative to those rules. Explain:
   - which earlier non-CONTINUE rules could stop it from ever being reached (shadowing),
   - which later rules it will now shadow,
   - which `%CONTINUE%` layers before it will already have modified `%NAME%`.
3. State the affected FILTLVL levels explicitly (e.g. "levels 8–12 only").
4. Check whether BIG_GG / REVEALED / POE_SOUNDS variants need different behavior.
5. Only then edit. Put the rule in the matching `// ===== Section =====` block.

## Things to never do
- Never invent item codes, stat IDs or keywords. Look them up in `docs/`, or in existing rules.
  If something is not documented, say so and ask.
- Never trust general Diablo 2 / D2R / other-mod knowledge for PD2 specifics. When the wiki and your
  prior knowledge disagree, the wiki wins; when the wiki and the author disagree, the author wins.
- Never change the season/version string in the Horadric Cube description unless asked.
- Never push to `main` without the author's explicit go-ahead: the launcher may serve it to players.
  Work on a branch.

## Communication
- The author knows PD2 and this filter far better than you. Ask when intent is ambiguous
  (which levels? which classes? which variants?) instead of guessing.
- When explaining a change, cite line numbers and the rules that interact with it.
